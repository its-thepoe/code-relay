## Dependency notes

- 001 comes first because the product must stop marking broken ZIPs as completed before deeper fidelity changes can be trusted.
- 002 depends on 001 because the UI warning should reference the new acceptance reality and avoid promising more than the backend can verify.
- 003 depends on 001 because truncation should become a blocking completed-job failure, not just another warning.
- 004 depends on 001 because evidence-level reporting should feed the same completion gate.
- 005 depends on 001 because the acceptance gate should reuse the generated install/build workflow instead of creating duplicate install steps.
- 006 repairs the current CMS compiler failure and adds a generator-branch compilation matrix. It depends on 005 because deterministic generated dependencies make that matrix reproducible.
- 007 blocks a full-site export when any discovered route is skipped or when desktop, laptop, tablet, or mobile capture evidence is missing or invalid. It can run independently of 006, but both must be complete before full-site is described as reliable.
- 008 changes the product direction of full-site exports: keep runtime assumptions, remove debug chrome from the shipped app, and optimize the handoff for the next agent instead of a human-first code cleanup story.
- 009 hardens the remaining weak point: heavy full-site routes and failed-job recovery. It splits capture into required and optional phases, adds resumable route/viewport checkpoints, and prevents minor failures from forcing whole-export reruns.
- 010 is the final release-hardening layer: reconcile the docs, finish the evidence-label/report wiring, validate representative generated builds, and compare the same published Framer URLs against `ditto.site` with a repeatable benchmark suite.

## Findings considered and rejected

- Full rewrite to "perfect Framer clone" exporter: rejected for now because the fastest trust repair is to block bad completions, expose truncation, and label evidence correctly before changing the whole architecture.
- Raising the plugin node cap as the primary fix: rejected because it hides the partial-capture invariant violation and can make job payloads, polling, and builds even heavier.
- Hiding full-site entirely: rejected because backend support exists and users may need it, but it must be labeled experimental and gated until fidelity improves.
- Treating the current job as a breakpoint failure: rejected. Its log shows all four capture passes and distinct tablet/mobile node counts, but it omits the width-validation artifact needed to prove the exact observed widths. Plan 007 makes that proof mandatory and reportable.
- Plan 003's historical 3,000-node cap: stale at current HEAD. The runtime-first full-site path no longer uses that cap; explicit plugin capture diagnostics and a page-root completion gate are retained as a regression safety rail.
